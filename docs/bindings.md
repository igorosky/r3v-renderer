# Bindings

[Back to README](../README.md)

The C, C++, Python and JavaScript bindings cover the same components as Rust
(see the [guide](guide.md)), with a few exceptions listed below.

Only one binding fits in a build: `c`/`cpp`, `python` and `js` cannot be
combined. `js` does not work with `multi-threaded`.

## Names

Every component maps 1:1 onto a handle (C) or a class (Python, JS). Classes are
named like the C types without the `R3v` prefix, and methods keep their
snake_case names.

| Rust | C | Python, JS |
|---|---|---|
| `renderer::WgpuAccelerated` | `R3vWgpuRenderer`, `r3v_wgpu_renderer_*` | `WgpuRenderer` |
| `renderer::WgpuAcceleratedConfiguration` | `R3vWgpuRendererConfiguration` | `WgpuRendererConfiguration` |
| `tesselator::CpuTesselator` | `R3vCpuTesselator`, `r3v_cpu_tesselator_*` | `CpuTesselator` |
| `camera::OrbitCamera` | `R3vOrbitCamera`, `r3v_orbit_camera_*` | `OrbitCamera` |
| `urdf::UrdfRobot` (parsed file) | `R3vUrdfDescription`, `r3v_urdf_*` | `UrdfDescription` |
| `robot::UrdfRobot` | `R3vUrdfRobot`, `r3v_urdf_robot_*` | `UrdfRobot` |
| `mesh::Mesh` | `R3vMesh`, `r3v_mesh_*` | `Mesh` |

Not available outside Rust: textures (`upload_texture`, `set_asset_texture`)
and the frustum culling switch of the renderer.

Loading files:

| | Meshes | URDF |
|---|---|---|
| C, C++ | `r3v_stl_read_file` (STL), `r3v_mesh_from_triangles` | `r3v_urdf_read_file`, `r3v_urdf_read_str` |
| Python | `Mesh.read_file` (STL or OBJ), `Mesh(triangles)` | `UrdfDescription.read_file`, `UrdfDescription.read_str` |
| JS | `Mesh.read_stl_bytes`, `new Mesh(triangles)` | `UrdfDescription.read_str` |

Inputs are duck typed in Python and JS, so r3v-voxelizer's own `PointI` and
`CompressedVoxelGroup` objects can be passed to the tesselator as they are.

## C and C++

```bash
cargo build --release --features c                   # or cpp, add ,multi-threaded for a threaded tesselator
cc -std=c11 -I bindings examples/c/voxels_to_ppm.c \
    -L target/release -lr3v_renderer -o voxels_to_ppm
LD_LIBRARY_PATH=target/release ./voxels_to_ppm stairs.ppm
```

Headers: `bindings/r3v-renderer.h` (C) and `bindings/r3v-renderer.hpp` (C++,
namespace `r3v::renderer`). Both are generated by cbindgen from
`src/bindings/c` when building with `c` or `cpp`.

Errors:

- Functions return an `R3vStatus`: `R3V_OK`, `R3V_INVALID_ARGUMENT`,
  `R3V_NOT_CONFIGURED`, `R3V_OUT_OF_RANGE`, `R3V_NOT_FOUND`, `R3V_FAILED` or
  `R3V_PANIC`. Functions that create a handle return NULL on failure.
- `r3v_renderer_last_error()` gives the reason of the last failure.
- Panics never unwind into C, they are reported like any other failure.

Ownership: every handle has a `_drop` function. `r3v_wgpu_renderer_update_geometry`
takes the delta, so do not drop it afterwards. `r3v_wgpu_renderer_upload_asset`
copies the mesh, so the mesh can be dropped right after.

## Python

```bash
cargo build --release --features python              # add ,multi-threaded for a threaded tesselator
cp target/release/libr3v_renderer.so r3v_renderer.so # .dylib on macOS
PYTHONPATH=. python3 examples/python/voxels_to_ppm.py stairs.ppm
```

- Errors are exceptions: `ValueError` for invalid arguments (nothing is changed
  then), `IndexError` for unknown instances, `RuntimeError` for a component
  used before it is configured and for failures such as reading a file or
  getting a GPU.
- Bulk data goes in and out as lists of objects. Only frames are written to a
  buffer you pass (`bytearray`, `memoryview`, numpy array, ...).
- Type stubs are in `bindings/r3v_renderer.pyi`, put the file next to
  `r3v_renderer.so`. `help(r3v_renderer)` shows the documentation of the
  module.

## JavaScript (WebAssembly)

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
wasm-pack build --release --target web --features js
```

`pkg/` gets the module and its TypeScript types.

Differences from the other languages:

- The renderer is created with `await WgpuRenderer.create()`, there is no
  constructor.
- `render` and `render_rgba` return Promises. `render_rgba` writes RGBA, ready
  for `ImageData`.
- While a render is pending, every other call on that renderer throws (and
  `render` rejects). Await each frame before the next call.
- `get_output_geometry_delta()` returns `undefined` when nothing changed.
- Inputs are read by property name, so plain objects work
  (`{ x, y, z, i }` for a block). Vectors are arrays of numbers.
- Data that only comes out (triangle chunks, URDF descriptions, robot
  transforms) is plain objects and arrays, so `structuredClone`, `postMessage`
  and `JSON.stringify` keep it.
- Errors are exceptions (or rejections for async methods): `TypeError` for an
  argument of the wrong type, `RangeError` for an invalid value or an unknown
  instance, `Error` for a component used before it is configured or while it
  renders, and for failures such as parsing a file or getting a GPU.

### Running on Node.js

Node.js has no WebGPU. The tests and the example take it from the `webgpu`
package (Dawn), installed by `npm ci` in `tests/js`:

```bash
(cd tests/js && npm ci)
node --import ./tests/js/webgpu.mjs examples/js/voxels_to_ppm.mjs stairs.ppm
```

The example loads the module from `pkg/`, or from `R3V_RENDERER_PKG` when set.
